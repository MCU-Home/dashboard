# 0010 — The flash-flow ladder; v0.1 stops at rung 1

- Status: draft
- Date: 2026-08-07

## Context

Firmware ADR 0016 fixed browser flashing over Web Serial as the product
goal and MCUHome's own SMP client as the thing that makes it possible.
One browser rule decides how that reaches the user:

**Web Serial requires a secure context** — `https`, `file`, or
loopback/localhost. `http://homeassistant.local:8123` is **not** one.
The most common way to reach a Home Assistant dashboard is therefore
precisely the way that cannot open a serial port. Support otherwise:
Chrome/Edge/Opera 89+, Firefox 151+ on desktop, Chrome Android ~M149;
Safari and iOS never.

**The pull direction is provably closed.** A hosted HTTPS page cannot
fetch firmware from a LAN dashboard: mixed content blocks it, and
Chrome's Local Network Access blocks what mixed content does not. Any
solution has to *push* from the dashboard tab.

**The push direction is shipped and proven twice.** ESPHome documents a
hosted HTTPS flasher page receiving the firmware by tab-to-tab
`postMessage` — transferable `ArrayBuffer`, `window.open` with a
`#nonce=` fragment, nonce plus `window.opener` check as authentication,
and a page CSP that forbids all server communication so the user can
verify the firmware is never uploaded. Home Assistant's own ZBT-1
updater uses the same pattern (NabuCasa's `sl-web-tools`, a fork of ESP
Web Tools). ESPHome's Device Builder offers four install paths side by
side, which is the shape of a mature answer, not of a first release.

## Decision

The flash flow is a **ladder**. The order is product-owner-fixed, and
**v0.1 stops after rung 1** — that is a vertical line, not a
prioritization.

### Rung 1 — v0.1: manual download and upload, only

The dashboard offers the artifact set for download, together with the
per-board instructions. Those instructions are **registry data**
generated by the builder (firmware ADR 0016: a board's `BoardDef` knows
its bootstrap mechanism, artifact format and instructions), so they
cannot drift from the artifacts actually produced. Flashing itself
happens through the vendor path or the CLI.

No in-page Web Serial and no hand-off ship in v0.1. The flash story of
the first release is a download button and a correct instruction.

### Rung 2 — post-v1.0: `postMessage` hand-off to a hosted flasher

At `flash-tool.mcuhome.org`. `window.open` with `#nonce=…&origin=…`;
the firmware travels as a transferable `ArrayBuffer`; the flasher
authenticates the message by nonce and `window.opener`; its CSP forbids
all outbound communication, so "this page cannot upload your firmware"
is a claim the user can check rather than trust.

Two browser properties turn this from a workaround into good UX, and
both are worth designing for rather than discovering:

- **Web Serial port permissions persist per origin**, so the flasher tab
  remembers the device the user already approved;
- **the channel lives as long as both tabs live**, so the flasher can
  register itself as a flash target in the dashboard and every
  subsequent flash is one click — with no server involved in either
  direction.

### Rung 3 — post-v1.0, on demand: an end-to-end encrypted tunnel

For the case rung 2 cannot serve: the browser doing the flashing is on a
different machine from the dashboard. A WebSocket tunnel through
`flash-tool.mcuhome.org` relays the image, and both the image's
**sha256** and a **one-time decryption key** travel in the URL fragment
— which never reaches the server. A compromised relay can therefore
neither read the firmware nor substitute it.

This rung needs real operated infrastructure, not a static Pages deploy.
It is built when the demand is real, and not before.

### The fallback never goes away

Manual file upload into the flasher stays available at every rung. It is
what a firewalled Home Assistant, an offline workshop machine, and every
Safari user have.

### MVP obligations, so that no rung is precluded

These are v0.1 requirements even though v0.1 uses none of the rungs
above it:

- **Stable, addressable artifact URLs** — and retention (ADR 0008) must
  make an expired one say so, never resolve to the wrong file.
- **A sha256 per artifact in the build manifest**, from day one
  (ADR 0006 decision 7).
- **Room in the WebSocket vocabulary for flasher-target registration** —
  a client must be able to announce itself as a flash target without a
  protocol break.

**Secure-context detection is what chooses** between in-page Web Serial
and hand-off, once rung 2 exists: a dashboard served over `https` or
localhost flashes in its own tab; anything else hands off.
`flash-tool.mcuhome.org` is reserved in the project's domain scheme. Its
repository, its Pages deployment and the versioned `postMessage`
contract — in lockstep with the SMP client of firmware ADR 0016 — are
created when rung 2 is built, not before (no dead links, and no
infrastructure without a service behind it).

## Consequences

- v0.1 ships a flash story that people will call primitive, and it ships
  on time. Every later rung is additive; none of them invalidates an
  artifact or a manifest produced by v0.1.
- Safari and iOS users never leave rung 1. Firmware ADR 0016 already
  commits to stating this where users choose their path.
- At rung 2 the project takes on operated infrastructure — a page whose
  `postMessage` contract must stay versioned against the SMP client for
  as long as MCUHome flashes devices. That cost is accepted at rung 2,
  deliberately not at rung 1.
- The "persistent flasher tab as a flash target" UX is available with no
  server at all, which is the reason rung 2 outranks rung 3 despite
  rung 3 being the more general mechanism.
- Related standing decisions: ADR 0006 (hashes, frame vocabulary),
  ADR 0008 (artifact retention and URLs); firmware ADR 0015 and
  ADR 0016 (Web Serial, the SMP client, per-board instructions).
